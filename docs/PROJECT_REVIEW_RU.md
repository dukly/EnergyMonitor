# Ревью EnergyMonitor

Дата: 18 октября 2026 года. Проверенная версия: `8a545d3`, ветка `main`.

Это исходный отчёт до исправлений. Результаты последующей работы и проверок —
в [FIX_VERIFICATION_RU.md](FIX_VERIFICATION_RU.md). Работа над профилями инверторов
отложена по отдельному указанию пользователя.

## Оценка состояния

Проект — небольшой агент сбора телеметрии одного инвертора: Modbus TCP → декодирование → SQLite. Базовая архитектура понятна, модули разделены, есть тесты и варианты установки. Стадия по результатам проверки — прототип/MVP агента. Готовность к непрерывной эксплуатации ещё требует исправлений установщиков, восстановления после сбоев и подтверждения карт регистров на конкретном оборудовании.

Это не полноценная система мониторинга с интерфейсом, сервером, уведомлениями и управлением парком устройств: таких компонентов в репозитории нет. Их необходимость зависит от назначения продукта.

## Что уже сделано

- Конфигурация через `.env` и окружение, типизация Pydantic Settings; относительные пути считаются от корня проекта.
- Modbus TCP клиент с Unit ID, таймаутом, повторами подключения, FC03/FC04 и запоминанием удачного типа регистров.
- Чтение большого блока с повторной попыткой частями при неудаче.
- Общая модель из 11 показателей: напряжение и ток DC, мощность AC, температура, частота, коэффициент мощности, суммарная/суточная энергия, время работы, статус, ошибка.
- Декодирование девяти float32 и двух 16-битных значений; отклонение NaN и коротких ответов.
- Периодический цикл, переподключение после потери связи во время работы, пропуск полностью пустых измерений.
- SQLite: создание каталога и таблицы, автоинкрементный ID, индекс времени, параметризованная запись.
- Миграция старой таблицы без ID, транзакционная защита миграции, восстановление оставшейся legacy-таблицы.
- Текстовые подписи статусов и ошибок, сохранение исходных кодов.
- Консольные логи, отдельный файл ошибок, ротация файлов.
- Шаблоны установки Linux/systemd, Windows/Task Scheduler, Docker Compose с томами данных и логов.
- README, инструкции установки и полевой проверки, CI на Python 3.12 с pytest и flake8.

Профили `default`, `deye`, `goodwe` присутствуют как конфигурационные записи. Это ещё не доказательство поддержки соответствующих моделей инверторов.

## Проверки и их границы

- Просмотрены все 12 Python-файлов `src` (816 строк), тесты, конфигурация CI, установщики и документация.
- `python -m pytest -q`: **15 passed**.
- `python -m flake8 src tests`: **ошибок нет**.
- Локальный запуск проверок: Python 3.14.2, pymodbus 3.11.4, pydantic-settings 2.7.1. CI настроен на 3.12; отдельный локальный прогон именно на 3.12 не выполнялся.
- Изолированно воспроизведены: принятие отрицательного интервала, принятие infinity, ошибка записи в частичную схему БД, штатный возврат при недоступности Modbus на старте, вложенная директория при повторном Copy-Item, отказ чтения `.env` с BOM.
- Дополнительно проведены независимые проверки ошибок и безопасности обычными проверяющими агентами. Специализированные инструменты Bugbot/Security Review недоступны; их запуск не заявляется.
- Подключение к инвертору не выполнялось. Карты регистров и режим шлюза на реальном устройстве не подтверждены. Не запускались реальная установка systemd/Task Scheduler и Docker, сканер CVE и длительный нагрузочный тест.
- Исходный код в ходе ревью не исправлялся; добавлен этот отчёт. Существующие пользовательские данные не изменялись.

## Обнаруженные проблемы

Приоритет P1 — исправить до штатного развёртывания; P2 — исправить для надёжной эксплуатации. Часть замечаний ниже — ограничения реализации, а не доказанные ошибки конкретного оборудования.

### 1. P1 — Windows-задача не запускается с путём по умолчанию

Место: `install/windows/install.ps1:36`.

Аргумент Python передаётся как строка пути без внутренних кавычек. Значение по умолчанию содержит `Program Files`; при запуске Python получает первым аргументом `C:\Program`, а не полный путь к `main.py`. Кавычки PowerShell вокруг строки не становятся кавычками внутри аргументов зарегистрированной задачи.

Нужно экранировать кавычки вокруг пути скрипта и проверить зарегистрированное действие запуском с путём, содержащим пробелы.

### 2. P1 — `.env` из Windows PowerShell 5.1 не читается

Место: `install/windows/install.ps1:24`, `src/config.py:39`.

`Set-Content -Encoding UTF8` в Windows PowerShell 5.1 записывает BOM. Конфигурация читается как `utf-8`: имя первого ключа становится `\ufeffMODBUS_HOST`, и Pydantic отклоняет его как лишнее поле. Приложение падает при импорте конфигурации. Отказ на BOM-файле воспроизведён; PowerShell 7 имеет другое поведение кодировки.

Нужно писать UTF-8 без BOM либо читать `utf-8-sig`; добавить проверку обеих поддерживаемых версий PowerShell.

### 3. P1 — повторная установка Windows не обновляет рабочий `src`

Место: `install/windows/install.ps1:14`.

При существующем `$InstallDir\src` команда Copy-Item копирует исходную папку внутрь и создаёт `src\src`. Рабочий `src\main.py` остаётся старым. Поведение воспроизведено на временных каталогах.

Нужно копировать содержимое директории с явной стратегией обновления и удаления устаревших файлов. Проверить сценарии первой установки и обновления отдельно.

### 4. P1 — поддержка брендов не подтверждена картами регистров

Место: `src/inverter_profiles/deye.py:5`, `src/inverter_profiles/goodwe.py:5`, `src/libraries/modbus.py:33`, `src/status_labels.py:1`.

Все профили читают 32000–32019 и используют одинаковые смещения, float32 big-endian и словари кодов. Профиль не может задать отдельные адреса полей, масштаб, знаковость, порядок слов, битовые ошибки и собственный декодер. Отличие Deye — выбор FC03/FC04. Тест профиля проверяет заданные константы, а не соответствие протоколу производителя.

Таким образом, наличие профилей не гарантирует достоверную телеметрию. Совпадение TCP-соединения и успешный ответ не доказывают правильность физических величин. Реальные карты моделей в рамках этого ревью не сверялись; утверждения, что конкретная модель обязательно не работает, здесь нет.

Нужно выбрать конкретные модель/прошивку, привязать поля к документации производителя, реализовать профильное декодирование и тесты на реальных дампах. Отдельно проверить совместимость Modbus TCP framing с выбранным режимом USR-W610.

### 5. P2 — недоступность инвертора при запуске останавливает агент

Место: `src/main.py:44–47`, `install/windows/install.ps1:37–38`.

После стартовых попыток подключения main возвращает None, процесс завершается с успешным кодом. В Windows-задаче не настроены повторы; после загрузки ПК раньше сети/инвертора сбор не возобновится автоматически. Linux и Docker маскируют проблему политикой перезапуска; ручной запуск также останавливается.

Нужно перенести первое подключение в устойчивый цикл с ограниченной задержкой повторов; при фатальной конфигурационной ошибке возвращать ненулевой код.

### 6. P2 — повторная установка Linux уничтожает настройки

Место: `install/gateway/install.sh:11`.

Шаблон всегда копируется поверх `.env`. Обновление возвращает адрес, профиль и пути к значениям примера. Windows-установщик также безусловно пересоздаёт `.env` (`install/windows/install.ps1:24`), теряя пользовательские дополнительные настройки.

Нужно сохранять существующий конфиг, генерировать шаблон только при первом запуске, а обновления конфигурации выполнять явно с резервной копией.

### 7. P2 — Linux INSTALL_DIR не соответствует systemd unit

Место: `install/gateway/install.sh:4`, `install/gateway/energy-monitor-agent.service:9–11`.

Установщик позволяет иной INSTALL_DIR, но unit всегда использует `/opt/energy-monitor-agent`. В результате сервис запускает старую установку или падает из-за отсутствующих файлов.

Нужно генерировать unit с фактическим каталогом либо отказаться от переопределения INSTALL_DIR.

### 8. P2 — неполная схема SQLite принимается, но запись невозможна

Место: `src/libraries/database.py:6–9,96–102`, `tests/test_handler.py` — тест частичной схемы.

Если таблица уже имеет `id`, добавляются только `status_text` и `error_text`. Отсутствие других колонок не проверяется. Схема из собственного теста с id/timestamp/voltage_dc/status/error успешно инициализируется, но первая запись падает: `table measurements has no column named current_dc`. В рабочем цикле ошибка повторяется при каждом опросе.

Нужно валидировать полный контракт таблицы или версионировать миграции. Тест должен выполнять запись после обновления схемы, а не только проверять две колонки.

### 9. P2 — настройки не имеют допустимых диапазонов

Место: `src/config.py:22–34`, `src/main.py:61`.

Проверяются типы, но отрицательный интервал принимается; `time.sleep(-1)` завершает агент. Нулевой интервал создаёт непрерывный опрос без паузы. Также нет ограничений для порта, таймаута, количества повторов и параметров ротации.

Нужно задать диапазоны и понятную диагностику до запуска клиента и логирования.

### 10. P2 — нечисловые и недостоверные значения могут попадать в БД

Место: `src/libraries/modbus.py:84–89`, `src/handler.py:11–24`.

NaN отвергается, но ±infinity принимается — воспроизведено. Если девять float-полей не декодировались, а status/error доступны, измерение также считается непустым и записывается. Качество записи отдельно не обозначается.

Нужно применять `isfinite`, профильные допустимые диапазоны и явно хранить качество/причину неполной записи. Частичные данные можно сохранять, если потребитель отличает их от полноценных измерений.

## Безопасность

В просмотренном коде не обнаружены HTTP API, выполнение команд на основании телеметрии, загрузка исполняемого кода из ответов или SQL-инъекции. Значения SQL параметризованы, используемые динамические идентификаторы фиксированы либо ограничены списком. Это результат статического анализа, не гарантия отсутствия любых уязвимостей.

Что стоит усилить:

- Linux unit запускает агент как root (`energy-monitor-agent.service:8`), Dockerfile не задаёт USER, Windows-задача использует Highest. Для чтения Modbus и записи своей БД обычно достаточно отдельной учётной записи с доступом к каталогам данных. Риск — больший ущерб при компрометации процесса; отдельная удалённая эксплуатация по коду не показана.
- Используется обычный ModbusTcpClient без настройки TLS/аутентификации. При возможности подменять сетевой трафик или контролировать конечную точку злоумышленник может подменять измерения. Нужны изолированная сеть и ограничение доступа к шлюзу; для удалённого доступа — защищённый канал.
- Зависимости верхнего уровня закреплены, транзитивные — нет; нет автоматической проверки известных уязвимостей. Сканирование CVE не выполнялось, наличие конкретной CVE не заявляется.
- Нужны явные права на `.env`, БД и резервные копии, особенно при установке в общий/пользовательски доступный каталог с привилегированным запуском.

## Что сделать дальше

### Этап 1 — добиться воспроизводимой установки и достоверных данных

1. Исправить кавычки, BOM и повторное копирование в Windows.
2. Сохранить `.env` при обновлениях и согласовать INSTALL_DIR с unit.
3. Обеспечить старт при временно недоступной сети и ненулевые коды фатальных ошибок.
4. Подтвердить одну конкретную модель инвертора: документация, сырые регистры, эталонные показания, единицы и масштаб. Непроверенные профили пометить как экспериментальные.
5. Расширить тесты для подтверждённых дефектов и выполнить smoke-тест первой/повторной установки на каждой поддерживаемой платформе.

Критерий завершения: чистая установка и обновление сохраняют настройки; после отсутствия сети на старте агент самостоятельно начинает сбор; показания совпадают с эталоном в заданном допуске.

### Этап 2 — обеспечить длительную автономную работу

1. Полная валидация конфигурации и схемы SQLite, версионирование миграций.
2. UTC-время с явным часовым поясом и временем фактического измерения. Сейчас записывается локальное время без зоны с секундной точностью (`handler.py:55`), что мешает объединению данных разных узлов и обработке перевода часов.
3. Контроль качества измерений, единиц, неполных записей, переполнений и некорректных кодов.
4. Статус последнего успешного опроса/записи, число ошибок, обнаружение устаревших данных. Сам по себе живой процесс ещё не доказывает, что данные поступают.
5. Retention, агрегирование и резервное копирование SQLite с проверкой восстановления. При интервале 5 секунд получается 17 280 записей в сутки, 6 307 200 в год на одно устройство; объём файла нужно измерить отдельно.
6. Проверить параллельное чтение БД, поведение при блокировке/заполнении диска и выбрать настройки SQLite под реальную нагрузку. WAL вводить по результату проверки, а не автоматически.
7. Корректная остановка SIGTERM, непривилегированный запуск, длительный тест с разрывами сети и перезагрузками шлюза.

Критерий завершения: длительный стендовый прогон, автоматически обнаруживаемые пропуски, восстановление после сбоев и проверенное восстановление из бэкапа.

### Этап 3 — развивать продукт по назначению

- Для локального регистратора: CLI диагностики, экспорт CSV, удобная проверка конфигурации, инструкция обновления/отката и журнал версий.
- Для мониторинга пользователя: API чтения, графики мощности/энергии, понятное состояние связи, уведомления о пропаже данных и авариях.
- Для нескольких устройств: идентификатор устройства в каждой записи, отдельные настройки подключения/профиля, независимые циклы и изоляция сбоев.
- Для центрального сервиса: надёжная доставка с буфером, подтверждением и дедупликацией; аутентификация и управление доступом. Сейчас передачи на сервер нет.
- Для поддержки новых инверторов: расширяемые профили с декодерами, источниками карт, моделями/прошивками и эталонными дампами.
- Для сопровождения: поддерживаемая версия Python, lock зависимостей, сканирование зависимостей, CI для Windows/Linux и контейнера, лицензия и правила релизов. Файла лицензии в просмотренном дереве нет.

Новые интерфейсы и серверные компоненты разумно начинать после подтверждения правильности и непрерывности первичных данных.
